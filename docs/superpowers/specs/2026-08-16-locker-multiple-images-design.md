# 물품보관함 다중 이미지 설계

## 목표

물품보관함 하나에 제한 없이 여러 장의 사진을 등록하고, 관리자 화면과 상세 조회 API에서 등록 순서대로 사진을 제공한다.

## 데이터 모델

- `locker_images` 테이블을 수동 DDL로 생성한다.
- 각 행은 `locker_id`, `image_url`, `list_order`, 생성·수정 시각을 가진다.
- `locker_id`는 `lockers.id`를 참조하며, 한 보관함은 여러 이미지 행을 가진다.
- `list_order` 오름차순으로 노출 순서를 결정한다. 수량 제한은 두지 않는다.
- 기존 `locker_details.image_url`은 이번 배포에서 제거하지 않는다. 값이 있으면 수동 배포 SQL로 `locker_images`의 첫 번째 이미지(`list_order = 0`)로 복사한다.

## 관리자 동작

- 등록·수정 폼은 다중 파일 선택을 허용한다.
- 기존 이미지와 새 선택 이미지를 함께 보여 주고, 각 기존 이미지를 삭제할 수 있다.
- 수정 저장 시 삭제 대상으로 선택한 이미지는 저장소와 DB에서 삭제하고, 새 파일은 기존 이미지 뒤에 등록한다.
- 보관함 삭제 시 연결된 모든 이미지 파일과 이미지 행을 삭제한다.
- 파일 형식 및 크기 검증은 기존 보관함 이미지 업로드 정책을 파일별로 재사용한다.

## 조회 API 호환성

- 보관함 상세 응답에 `imageUrls` 배열을 추가하며 순서는 `list_order` 오름차순이다.
- 기존 단일 `imageUrl` 필드는 첫 번째 이미지 URL을 반환해 기존 클라이언트 호환성을 유지한다.
- 이미지가 없으면 `imageUrls`는 빈 배열이고 `imageUrl`은 `null`이다.

## 수동 배포 DDL

애플리케이션 마이그레이션은 추가하지 않는다. 배포 시 아래 SQL을 수동 실행한다.

```sql
CREATE TABLE locker_images (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    locker_id BIGINT NOT NULL REFERENCES lockers(id),
    image_url VARCHAR(500) NOT NULL,
    list_order INTEGER NOT NULL,
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL,
    CONSTRAINT uk_locker_images_locker_order UNIQUE (locker_id, list_order)
);

CREATE INDEX idx_locker_images_locker_order
    ON locker_images (locker_id, list_order);

INSERT INTO locker_images (locker_id, image_url, list_order, created_at, updated_at)
SELECT locker_id, image_url, 0, CURRENT_TIMESTAMP, CURRENT_TIMESTAMP
FROM locker_details
WHERE image_url IS NOT NULL AND TRIM(image_url) <> '';
```

## 테스트

- 도메인 엔티티가 이미지 추가·삭제·순서 유지 동작을 수행하는지 검증한다.
- 관리자 수정이 새 이미지 추가와 선택 이미지 삭제를 처리하는지 검증한다.
- 상세 API가 전체 `imageUrls`와 첫 번째 `imageUrl`을 함께 반환하는지 검증한다.
